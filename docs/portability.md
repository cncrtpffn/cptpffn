# Переносимость: правила на случай порта

Возможно, демку перенесут на нативный игровой движок. Какой — пока не решено (Unity, Godot,
Unreal, свой). Правила ниже не зависят от движка. Они держат ядро игры в такой форме, чтобы его можно было
переписать почти один в один и сверить с оригиналом по эталонам. Все они полезны и без переноса.

Оценка порта на Unity — [native-port/unity-analysis.md](native-port/unity-analysis.md).
Задача порта — [backlog/14-native-port.md](backlog/14-native-port.md).

## Правила (действуют всегда)

1. **Чистое ядро.** В `src/physics` и `src/tutorial` нет three, `document`, `window` и DOM.
   Новая логика игры (физика, правила, квесты, ассистент, NPC) пишется туда же и в том же виде.
   Отрисовка и UI только читают состояние ядра и передают ему команды.
2. **Генерация мира — через сид.** Новая случайность в генерации мира (рельеф, флора, постройки)
   берёт числа из генератора с сидом, а не из `Math.random`. Тогда мир повторяется: скриншоты сравнимы,
   а после порта мир будет тем же. Чисто визуальные эффекты (брызги, частицы) могут брать `Math.random`.
3. **Данные — данными.** Квесты, карты, тексты и настройки описываются простыми объектами, которые
   сериализуются в JSON. Функции и замыкания в данных — только там, где без них нельзя.
4. **Одна формула — одно место.** Если формула нужна и на CPU, и в шейдере (волны), её параметры
   хранятся в одном месте, а не копируются.
5. **Оси и единицы — по таблице ниже.** Новый код не вводит своих соглашений.
6. **Не делать заранее:** переводить проект на TypeScript, переписывать отрисовку «под движок», дробить
   `main.js` ради будущего порта. Это дорого и сейчас ничего не даёт.

## Оси и единицы

| Что | Соглашение |
|---|---|
| Мир | x — восток, z — юг, y — вверх (three.js, правосторонняя система) |
| Курс лодки `psi` | 0 = север, по часовой; нос смотрит в `(sin psi, −cos psi)` по (x, z) |
| Ветер | компасное направление, **откуда** дует (`src/physics/wind.js`) |
| Углы | внутри кода — радианы; в конфигах, URL и UI — градусы (`DEG` из `src/config.js`) |
| Длина, скорость | метры, м/с; узлы — только в UI |

При переносе в левостороннюю систему (Unity: y вверх, z вперёд) все знаки поворотов и осей надо
проверить по этой таблице.

## Подготовка к порту

Подробности и порядок — в задаче [14](backlog/14-native-port.md), этап 0.

**Стоит сделать сейчас** (дёшево, полезно уже сегодня):

1. **Проверка чистоты ядра** в jsc: `src/physics` и `src/tutorial` не импортируют three и не трогают DOM.
   Сейчас правило 1 держится на дисциплине.
2. **Эталонные трассы в JSON.** `run-polar`, `run-collide` и `run-quests` сохраняют результаты в файлы:
   состояние лодки по времени, поляры, время прохождения уроков ботом. Порт сверяется с этими файлами,
   а уже сейчас они ловят случайные изменения физики. Это самая ценная подготовка.
3. **Квесты как данные.** Условия шагов сейчас — функции (`check: () => C.reach('sk-s', 10)`).
   Объектами (`check: { reach: ['sk-s', 10] }`) уроки и миссии становятся чистым JSON, который прочтёт
   любой движок и позже — редактор уроков. Объём: 13 квестов и разбор условий в `conditions.js`.

**Когда будем трогать эти места:**

4. Сид вместо `Math.random` в `src/scene/flora.js` и `src/scene/structures/` (правило 2).
5. Экспорт моделей в `.glb` из вьюеров (`GLTFExporter`), заодно для Blender.
6. Единая спецификация волн (`src/physics/waves.js` и шейдер воды) и тест, сверяющий CPU с GPU.
